# Runbook

Last updated: 2026-09-10

This runbook is for current setup and operations. Future roadmap details live in
`docs/ROADMAP.md`; implementation truth lives in `docs/STATUS.md`.

## Safety First

- Do not commit `~/.config/home-stack/env.local`, logs, generated certs, app data, databases, or secrets.
- Caddy's native Admin API must stay local-only at `127.0.0.1:2019`.
- Use config reload for registry/engine-generated Caddyfile changes. Use launchd restart only for Caddy binary upgrades or daemon-level environment/process changes.
- Phase A/B Makefile targets are local harnesses only. Production services should run through launchd foreground wrappers.
- Do not stop or reuse interim manual sessions on ports `3000` and `4096`; they may be active OpenChamber/OpenCode sessions.

## Prerequisites

- macOS with Homebrew.
- Tailscale installed, active, and logged in.
- Cloudflare API token scoped to edit DNS for the target zone.
- Go installed.
- OpenCode and OpenChamber installed in the paths resolved by `HOME_STACK_PATH`.

## Build Caddy

Home Stack uses a custom Caddy binary with the Cloudflare DNS plugin.

```bash
brew install go
go install github.com/caddyserver/xcaddy/cmd/xcaddy@latest
mkdir -p portable/home-stack/bin
CGO_ENABLED=0 GOARCH="$(uname -m | sed -e 's/^x86_64$/amd64/' -e 's/^aarch64$/arm64/')" \
  ~/go/bin/xcaddy build \
    --with github.com/caddy-dns/cloudflare \
    --with github.com/tailscale/caddy-tailscale \
    --output portable/home-stack/bin/caddy-cloudflare
```

Do not replace this with a stock Homebrew Caddy binary; DNS-01 depends on the plugin.

## Secrets And Local Config

Secrets live in `~/.config/home-stack/env.local` with `0600` permissions.
This file must contain secrets only — identity keys such as `HOME_STACK_PARENT_DOMAIN`
must not appear here; those live in the profile (`profiles/<name>/home-stack.env`).

Use the helper when possible; it creates a timestamped backup and does not print secret values:

```bash
portable/home-stack/scripts/env-set.sh HOME_STACK_ADMIN_PASSWORD
portable/home-stack/scripts/env-set.sh HOME_STACK_CLOUDFLARE_API_TOKEN
```

Required secrets:

- `HOME_STACK_ADMIN_PASSWORD` — required for Admin Basic Auth.
- `HOME_STACK_CLOUDFLARE_API_TOKEN` — Caddy DNS-01 issuance and Phase D tunnel.

Conditional (when the corresponding service/auth mode is configured):

- `HOME_STACK_OPENCODE_SERVER_PASSWORD` — passed to OpenCode/OpenChamber when backend auth is enabled.
- `HOME_STACK_OPENCHAMBER_UI_PASSWORD` — OpenChamber UI credential when flag is on.

Required when the managed Hermes service is deployed:

- `HOME_STACK_HERMES_DASHBOARD_PASSWORD_HASH` — official Hermes scrypt hash; no server plaintext password is stored.
- `HOME_STACK_HERMES_DASHBOARD_SECRET` — stable 32-byte-or-longer signing secret so native sessions survive restarts.

`HOME_STACK_HERMES_DASHBOARD_USERNAME` and `HOME_STACK_HERMES_PORT` are
tracked non-secrets in the profile. `env-set.sh` shell-quotes values, so the
`$` separators in a scrypt hash round-trip safely through `env.local`.
`run-hermes.sh` resolves these values and then starts Hermes under a clean
environment allowlist. Unrelated values from `env.local` are not inherited by
the agent process. Model, tool, messaging, and provider credentials belong in
Hermes' own protected configuration rather than home-stack.

Tracked non-secret profile values live under `profiles/<profile>/`, e.g.
`profiles/<name>/home-stack.env` and `profiles/<name>/services.yaml`. Only
`profiles/default/` is tracked in this repository; a real profile is
gitignored by design (`docs/PUBLIC_RELEASE.md` §4) and belongs in your own
dotfiles overlay.

## Install Or Refresh launchd Services

Launchd plists are regenerated by `hs sync` (gitignored runtime state, not checked-in
source). Run `hs sync` before installing if you have just changed the profile or registry.

Validate wrappers and generated plists before loading:

```bash
bash -n portable/home-stack/scripts/run-opencode.sh portable/home-stack/scripts/run-openchamber.sh portable/home-stack/scripts/run-hermes.sh portable/home-stack/scripts/run-caddy.sh
plutil -lint portable/home-stack/launchd/*.plist
```

Install plist files without starting services:

```bash
portable/home-stack/scripts/install-launchd.sh
```

Install and start services:

```bash
portable/home-stack/scripts/install-launchd.sh --load
```

`--load` converges rather than restarting everything: anything not currently
loaded is started, a service whose plist changed is reloaded, and a running
service whose plist is byte-identical is left alone. It compares plists, so it
cannot see a rebuilt binary sitting behind an unchanged plist -- restart those
explicitly with `hs restart <service>`.

### Upgrading services whose plists changed

`hs restart <service>` is `launchctl kickstart -k`: it re-execs the already
loaded job **under its existing environment**. launchd only re-reads a plist
on `bootstrap`, so if `hs sync` regenerated a service's plist with new or
changed `EnvironmentVariables` (for example, the engine-injected
`HOME_STACK_SELF_URL`/`HOME_STACK_SELF_HOST`/`HOME_STACK_DATA_DIR` keys), a
plain `hs restart` -- or the Admin "Restart" button, which drives the same
path -- brings the process back up with the *old* environment. A reboot has
the same effect: it loads whichever plist is currently installed, not
whatever `hs sync` most recently generated.

After `hs sync`, converge the installed plists with their generated versions
before restarting anything:

```bash
portable/home-stack/scripts/install-launchd.sh --load
```

A byte-identical plist is left alone (no bootout, no downtime); a changed
agent is booted out, awaited (`home_stack_wait_label_gone`) so the teardown
finishes before the new plist is bootstrapped, then brought up under the new
environment; the Caddy daemon is cycled once unconditionally on every
`--load`. This is the only path that is proven safe against launchd's
asynchronous `bootout`.

The per-agent alternative -- `hs stop <service>` followed later by
`hs start <service>` -- is **not** race-safe: `service-launchd.sh`'s
`do_stop` fires `launchctl bootout` and returns immediately, without waiting
for teardown (`home_stack_wait_label_gone` is used only by `do_restart`'s
not-loaded fallback and by `install-launchd.sh --load`). A `start` issued
right after can still see the label as tearing down and fail to bootstrap
("Bootstrap failed: 5: Input/output error"), or transiently succeed while the
old process is still exiting. Prefer `install-launchd.sh --load` whenever a
plist changed; if you must go per-service, insert a manual wait (or poll
`launchctl print <domain>/<label>` until it errors) between `stop` and
`start` rather than assuming the sequence is safe as written today.

Unload and remove plist files:

```bash
portable/home-stack/scripts/uninstall-launchd.sh --unload
```

Install for a different macOS username:

```bash
HOME_STACK_OWNER_HOME=/Users/alice portable/home-stack/scripts/install-launchd.sh
```

## Registry-Driven Sync Workflow

Edit the registry, then sync:

```bash
# 1. Edit profiles/<name>/services.yaml
#    Use `subdomain:` for services under your parent domain;
#    `host:` for external hostnames not under the parent domain.

# 2. Sync — regenerates Caddyfile, catalog.json, launchd plists from the active profile.
portable/home-stack/scripts/hs sync

# 3. Validate the generated Caddyfile (without using a real token).
CLOUDFLARE_API_TOKEN=dummy portable/home-stack/bin/caddy-cloudflare \
  adapt --config portable/home-stack/Caddyfile

# 4. Reload running Caddy without restarting.
portable/home-stack/scripts/hs reload caddy
```

Verify expected hosts and an unknown wildcard host after reload. Unknown
`*.<your-domain>` hosts should abort to reduce fingerprinting.

There is no production Caddyfile template fallback. For recovery, restore the
registry/source change, run `hs sync`, validate the generated Caddyfile, and
reload Caddy.

## Hermes Agent: Reviewed Installation And Deployment

A deployed Hermes profile reports the official Hermes Agent checkout it
installed (version and commit); record that pin, the generated LaunchAgent's
load state, the raw authenticated endpoint, and the Caddy route in your
overlay's `INSTALLED.md` once installed. State remains under `~/.hermes` and
does not vary by version.

The login username is operator-chosen. Only its scrypt hash is stored
server-side. Store the client plaintext as a website login for the dashboard's
HTTPS route in Apple Passwords/iCloud Keychain so Safari and enrolled Apple
devices can sync/autofill it. A generic-password item in the local `login`
keychain is a different record type and is not the supported cross-device
recovery source. Direct Pocket ID OIDC can also be enabled; Basic remains the
break-glass provider and must be rotated if its saved plaintext no longer
matches the server hash. Record your own credential-rotation history in your
overlay's `hermes-deployed.md`, not here.

The intended iPhone app, `goncharik/hermes-mobile`, is a community client for
the official Hermes dashboard API, not an official Nous Research app. Its
current login flow requires the Basic username/password provider; it does not
support the dashboard's self-hosted OIDC flow. Configure its server as your
dashboard's HTTPS route. The app keeps the authenticated session cookie in the
device Keychain and does not persist the plaintext password. Its own session
record is not explicitly iCloud-synchronizable, while the separate Apple
Passwords website credential can sync and provide Autofill/recovery. Leave the
app's optional third-party push-notification gateway disabled until its
additional privacy and reliability boundary is separately reviewed. Record
your own validation status for this client in your overlay's
`hermes-deployed.md`.

Fresh installs and upgrades use two separate review boundaries.

### Boundary 1: external installer

Official source:

- Repository: `https://github.com/NousResearch/hermes-agent`
- Reviewed installed checkout: pick a released tag or a reviewed post-release
  `main` commit; record the commit in your overlay's `INSTALLED.md`.
- Installer source: `https://github.com/NousResearch/hermes-agent/blob/<FULL_SHA>/scripts/install.sh`
- Dashboard reference: `https://hermes-agent.nousresearch.com/docs/user-guide/features/web-dashboard`

The reviewed command pins both the downloaded installer and the checkout, and
includes `--skip-setup` so API-key/OAuth setup is never run unattended:

```bash
curl -fsSL https://raw.githubusercontent.com/NousResearch/hermes-agent/<FULL_SHA>/scripts/install.sh \
  | bash -s -- --skip-setup --commit <FULL_SHA>
```

Changing that commit is a new external-install review, not an implicit
update; record the new commit in your overlay's `INSTALLED.md`.

On a normal non-root macOS install, the current official script clones into
`~/.hermes/hermes-agent`, creates `~/.hermes/hermes-agent/venv`, installs its
managed `uv` under `~/.hermes/bin`, creates Hermes config/state under
`~/.hermes`, writes launchers under `~/.local/bin`, and may add that launcher
directory to `.zshrc`/`.zprofile` if absent. It may download Python/package,
Node, browser, and frontend dependencies. Home-stack already includes
`~/.local/bin` in `HOME_STACK_PATH`.

The dashboard needs the official web and PTY extras. After the base installer
is reviewed and succeeds:

```bash
cd ~/.hermes/hermes-agent
~/.hermes/bin/uv pip install --python venv/bin/python -e '.[web,pty]'
```

Do not run `hermes setup` unattended. Stop here for the operator to configure
model/API credentials interactively later.

Generate the supported scrypt hash without placing the plaintext password in
shell history, then generate a stable signing secret. Neither command prints
the secret value through home-stack:

```bash
( cd ~/.hermes/hermes-agent && \
  venv/bin/python -c 'from getpass import getpass; from plugins.dashboard_auth.basic import hash_password; print(hash_password(getpass("Hermes dashboard password: ")))' \
) | portable/home-stack/scripts/env-set.sh HOME_STACK_HERMES_DASHBOARD_PASSWORD_HASH

openssl rand -base64 32 \
  | portable/home-stack/scripts/env-set.sh HOME_STACK_HERMES_DASHBOARD_SECRET
```

### Boundary 2: live infrastructure

Before applying anything, review `hs deploy --preview` (or the equivalent
generated diff) for exactly one new Caddy route, one Hermes LaunchAgent, and
the catalog entry. Then separately approve:

1. `hs sync` (writes generated artifacts and reloads Caddy);
2. generated plist linting and `install-launchd.sh` (plist installation);
3. loading only the Hermes LaunchAgent; and
4. any Caddy reload/restart not already performed by sync.

The wrapper binds `HOME_STACK_TAILNET_IP`, never `0.0.0.0`, and executes:

```text
hermes dashboard --host <tailnet-ip> --port 31511 --no-open
```

Before that exec, the wrapper replaces the inherited environment with an
allowlist. A repository test places fake Admin and Cloudflare credentials in
the loaded secret layer and fails if Hermes receives either value or any
`HOME_STACK_*` variable.

Hermes' staged personal, remote-operator, coding-worker, general-CLI, gateway,
and automation rollout is specified in `docs/HERMES_OPERATING_MODEL.md`.

The Hermes-owned operator baseline is deliberately configured outside the Home
Stack registry and shared environment: model/provider routing, auxiliary model
assignments, price/privacy routing constraints, memory and skill-write
approvals, and delegation bounds are all Hermes-owned settings. General CLI
access may be enabled per `docs/HERMES_OPERATING_MODEL.md`. Messaging
platforms, webhooks, cron tool access, computer-use, image generation, and MCP
servers should stay off until deliberately reviewed and enabled. The
separately supervised gateway service is documented below. Inspect resolved,
non-secret state with:

```bash

hermes config check
hermes tools list
hermes fallback list
hermes doctor
hermes security audit
```

Record your own provider/model routing, memory/approval settings, and update
history in your overlay's `hermes-deployed.md` rather than here. When
upgrading, follow the same reviewed-update pattern as a fresh install: back up
config, run the pinned installer/`hermes update` against a reviewed commit,
converge the locked environment if the updater's editable install drifts from
its own lock (`uv sync --extra all --locked`), and re-run `hermes security
audit` before trusting the result.

### Official messaging/cron gateway

The gateway is an internal Hermes worker, not another Tailnet web service.
Home Stack continues to supervise the exposed dashboard; Hermes' official
generator owns `~/Library/LaunchAgents/ai.hermes.gateway.plist`. Do not add a
`hermes-gateway` registry entry or handcrafted plist: that would duplicate the
upstream supervisor and its profile/update semantics.

Review and install the official user service separately:

```bash
hermes gateway install --force
plutil -lint ~/Library/LaunchAgents/ai.hermes.gateway.plist
hermes gateway status
```

On current macOS builds the generic `--start-now`/`--start-on-login` flags are
not consulted: installation writes a `RunAtLoad` plist and bootstraps it
immediately. Treat `hermes gateway install --force` as both plist replacement
and live service load; preview and approve both effects together.

The plist should contain only `HERMES_HOME`, `PATH`, and `VIRTUAL_ENV`, execute
the managed Python module with `gateway run --replace`, work from
`~/.hermes`, and log to `~/.hermes/logs/gateway{,.error}.log`. It has
`RunAtLoad`, `KeepAlive`, a 30-second restart throttle, a 25-second graceful
exit window, and the configured file-descriptor limit. The gateway opens no
listener merely by running; with no messaging platform it remains alive for
cron and housekeeping. `hermes gateway setup` is interactive and is the
supported path for adding a platform. Configure a platform-specific sender
allowlist and never use `GATEWAY_ALLOW_ALL_USERS=true` as a setup shortcut.

Gateway configuration, platform tokens, pairing state, sessions, cron jobs,
and logs remain under `~/.hermes`; none belong in Home Stack env, registry,
generated plists, or git. The dashboard's `/api/status` is the primary summary
surface. Webhooks and any platform that adds a listening port require a new
network/routing review.

Hermes only invokes its smart-approval reviewer for commands matched by the
built-in dangerous-command detector. `approvals.smart_policy` refines that
review; it is not a general command interceptor. The hard-deny rules should
cover obvious direct credential-store, Keychain-password, and full-environment
dumps. Do not describe the agent as sandboxed. Running the gateway does not by
itself authorize cron jobs, webhooks, arbitrary senders, or additional tools.
Record your own configured hard-deny rules in your overlay's
`hermes-deployed.md`.

The registry's literal Tailnet upstream is intentional because registry YAML
is pure data and has no shell interpolation. `proxy_identity: upstream`
rewrites only upstream `Host` and `Origin` for Hermes' DNS-rebinding guard;
Caddy still supplies its normal forwarded host/protocol/client headers and
natively tunnels WebSockets.

After installing, confirm the isolated preview (`hs deploy --preview`) shows
exactly one new Caddy route, one Hermes LaunchAgent, and one catalog entry
before applying; record the outcome of your own sync in your overlay's
`INSTALLED.md`.

### Portal projection deployment

Portal is a static build in `~/github/home-portal/dist`. Home Stack owns only

1. Build and test Portal in its own repository with `npm run check` and
   `npm run test:browser`.

4. Review `hs deploy --preview`; the Portal host should gain only exact catalog

build, rebuild Admin, run `hs sync`, and restart Admin. Generated artifacts are
not the rollback authority.

## Upgrade Workflow

Home-stack services are launchd-supervised, so upgrades must update the binary
launchd actually runs and then restart or reload intentionally. Every service
that carries an `install:` block in the registry (see
`docs/SERVICE_INTERFACE.md` §4d) is tracked by `hs upgrade`, which is the
starting point for all of the below:

```bash
hs upgrade status            # live / pinned / latest / drift, one row per install:-tracked service
hs upgrade status --check    # same, but exits 1 if anything is "behind" (for a cron/doctor check)
hs upgrade <service> --dry-run   # print the exact steps and resolved URLs/paths, touch nothing
hs upgrade <service> [--to <version>]
```

`hs upgrade` runs one reviewed procedure per `install.method`, implemented in
`portable/home-stack/scripts/lib/upgrade.sh`. It backs up the previous binary
(`.prev`), verifies the new one where it can, restarts the service, waits for
its registry health signal, and **auto-reverts** on a failed health check. What
each method actually does, and what still needs a human, is documented per
service below — read this before running the command on an identity-layer
service for the first time.

| Method | Automated by `hs upgrade` | Still manual |
|---|---|---|
| `github-release` (Pocket ID) | Resolve tag, download, checksum (if published), swap with `.prev`, verify `version_cmd`, restart, health check, revert on failure | Reviewing the release notes before running it |
| `xcaddy` (Caddy) | Build with the two plugins, `caddy adapt` against the live Caddyfile, swap with `.prev` | Restarting the daemon: Caddy is a LaunchDaemon, so `hs upgrade caddy` stops and prints the exact `sudo launchctl kickstart` command rather than restarting itself |
| `source-go` (tinyauth) | Clone at tag, `corepack pnpm` build the frontend, `go build`, swap with `.prev`, restart, health check, revert on failure | Re-checking upstream release notes (5.1.3 was itself a security fix) |
| `npm-global` (OpenChamber) | `npm install -g <pkg>@<version>`, restart, health check | Rollback (no `.prev` for a global npm package — reinstall the previous version by hand) |
| `opencode` | `opencode upgrade`, restart, health check | Nothing beyond reviewing what changed |
| `hermes-pinned` (Hermes) | The exact pinned-installer procedure below, gated behind `--yes` and a full commit SHA | Everything here is already a human-reviewed step by design — see below |
| `brew` | Status/drift only (`brew info --json=v2`) | The upgrade itself: run `brew upgrade <formula>` |

The rest of this section is what each command above actually runs, for the
services with a reviewed procedure worth reading in full.

### Pocket ID

`hs upgrade pocket-id` is `github-release` end to end: resolves the latest (or
`--to`) tag, downloads `pocket-id_darwin_{arch}`, verifies it against the
release's `checksums.txt` when one is published (loudly warns if not), backs
up the current binary to `.prev`, installs, confirms `pocket-id --version`
reports the target, restarts, and waits on its `/healthz` check — reverting
automatically if that fails. Equivalent by hand, per the original install
recipe:

```bash
VER=$(gh release view -R pocket-id/pocket-id --json tagName -q .tagName)
gh release download -R pocket-id/pocket-id "$VER" -p pocket-id_darwin_arm64 -p checksums.txt -D /tmp
shasum -a 256 -c <(grep pocket-id_darwin_arm64 /tmp/checksums.txt)
cp portable/home-stack/bin/pocket-id portable/home-stack/bin/pocket-id.prev
install -m 0755 /tmp/pocket-id_darwin_arm64 portable/home-stack/bin/pocket-id
portable/home-stack/scripts/service-launchd.sh restart pocket-id
```

### tinyauth

`hs upgrade tinyauth` is `source-go`: clones the target tag, builds the
frontend, `go build`s it exactly like the original from-source recipe below,
swaps with `.prev`, restarts, and health-checks — reverting on failure. Always
re-read the release notes before picking a tag; 5.1.3 was itself a fix for a
path-handling access-control bypass.

```bash
git clone --depth 1 --branch v5.1.3 https://github.com/tinyauthapp/tinyauth /tmp/tinyauth-src
cd /tmp/tinyauth-src/frontend && corepack pnpm install --frozen-lockfile && corepack pnpm run build
cd .. && cp -r frontend/dist internal/assets/
CGO_ENABLED=0 GOOS=darwin GOARCH=arm64 go build -tags nomsgpack -ldflags "-s -w" \
  -o portable/home-stack/bin/tinyauth ./cmd/tinyauth
portable/home-stack/scripts/service-launchd.sh restart tinyauth
```

### Hermes (commit-pinned only)

> Observed 2026-09: `install.sh --commit <sha>` can leave the checkout on the
> tip of `main` rather than the requested commit. `hs upgrade hermes` pins the
> checkout explicitly and verifies `HEAD`; if you run the installer by hand,
> follow it with `git -C ~/.hermes/hermes-agent checkout --detach <sha>` and
> reinstall the extras. After restarting, run `hermes gateway start` so Hermes
> regenerates its own gateway plist (it reports "stale" otherwise), and allow
> the first boot a minute — it rebuilds the web UI before listening.

`hs upgrade hermes --to <full-sha> --yes` runs exactly the procedure below; it
refuses a tag or any ref shorter than a full 40-character commit, and refuses
to run at all without `--yes` since it mutates `~/.hermes`. `--dry-run` prints
every step without touching anything.

1. Review the new official tag, full commit, and that commit's `install.sh`.
   Do not use a moving `main` installer or `hermes update` for production.
2. Back up config before any schema migration:

```bash
stamp="$(date +%Y%m%d-%H%M%S)"
cp -p ~/.hermes/config.yaml ~/.hermes/config.yaml.pre-upgrade.$stamp
```

3. Run the newly reviewed installer with both its raw URL and `--commit`
   pinned to the same full SHA, always retaining `--skip-setup`; then reinstall
   the dashboard extras:

```text
curl -fsSL https://raw.githubusercontent.com/NousResearch/hermes-agent/<FULL_SHA>/scripts/install.sh \
  | bash -s -- --skip-setup --commit <FULL_SHA>

cd ~/.hermes/hermes-agent
~/.hermes/bin/uv pip install --python venv/bin/python -e '.[web,pty]'
hermes config check
```

4. Review any proposed config migration interactively, restart through
   `hs restart hermes` or Admin, and repeat every Hermes check in
   `docs/VERIFICATION.md`. Do not accept an upgrade unless the listener remains
   exact-IP-only and `/api/status` still reports `auth_required: true` plus
   `basic`.

Hermes rollback/recovery uses the last known-good commit rather than generated
plists or hand-edited launchd state. Re-run the last reviewed pinned installer
and web/PTY command above with that commit, restore the pre-upgrade
`config.yaml` if the schema migration is incompatible, then restart Hermes.
The installer preserves `~/.hermes` sessions/state and home-stack preserves the
Keychain password, scrypt hash, and signing secret. If a wrapper or registry
change caused the failure, restore that source change, run `hs sync`, reinstall
only the changed generated plist, and verify before loading.

## Identity Layer

### Verify root-side WhoIs (do this first)

`tailscale_auth` resolves identity through the tailscaled LocalAPI. Caddy runs
as a root LaunchDaemon, so root must be able to reach it. On macOS that API is
TCP plus a token file (`/Library/Tailscale/ipnport` and `sameuserproof-<port>`),
not a unix socket. Confirmed working as the console user; confirm as root:

```bash
sudo tailscale whois "$(tailscale ip -4)"
```

A resolved user means Tier 1 works end to end: the CLI reaches tailscaled over
the same LocalAPI the Caddy plugin uses, so root succeeding here proves the
root-run daemon can too. Record the result of your own verification in your
overlay's `INSTALLED.md`. If it fails, do not abandon `auth: tailnet` —
instead run a small WhoIs shim as a LaunchAgent
under your own user and have the engine emit `forward_auth` to it. Same registry
field, same zero-click behaviour.

### Install Pocket ID

```bash
VER=$(gh release view -R pocket-id/pocket-id --json tagName -q .tagName)
gh release download -R pocket-id/pocket-id "$VER" -p pocket-id_darwin_arm64 -p checksums.txt -D /tmp
shasum -a 256 -c <(grep pocket-id_darwin_arm64 /tmp/checksums.txt) 
install -m 0755 /tmp/pocket-id_darwin_arm64 portable/home-stack/bin/pocket-id
portable/home-stack/scripts/env-set.sh HOME_STACK_POCKET_ID_ENCRYPTION_KEY "$(openssl rand -hex 32)"
```

Then create the first admin. A new instance has zero users, and because login
is passkey-only the normal login page has nothing to authenticate against —
there is no bootstrap password and no CLI path. The first account is created at
a separate setup page, which stops working once an admin exists:

    https://id.<your-domain>/setup

Use a device with an authenticator (Touch ID / Face ID / a security key). It has
to be the real HTTPS hostname, not `127.0.0.1:31520`: WebAuthn binds each
credential to its origin, so a passkey enrolled against loopback will not work
through Caddy.

`pocket-id one-time-access-token <user>` issues a recovery link for an account
that already exists — it cannot create the first one.

### Cutover to the identity-layer ingress

Order matters. `hs sync` regenerates the live Caddyfile **and reloads Caddy**, so
the plugin-capable binary has to be in place first — the current ingress binary
cannot load `tailscale_auth`, and syncing before the swap leaves a config it
will crash-loop on at the next restart.

```bash
portable/home-stack/scripts/cutover-identity.sh
```

### Wire Hermes to the identity layer

Hermes integrates with Pocket ID **directly** rather than through the broker:
it speaks OIDC itself, a direct client lets Pocket ID apply per-client
authorization (everything behind the broker arrives as one client), and it
keeps the broker off the path of a service whose CLI and native clients never
traverse Caddy.

Register a client in Pocket ID:

- Callback URL: `https://hermes.<your-domain>/auth/callback` — the plugin
  hard-validates that the path ends in `/auth/callback` and refuses otherwise.
- Public client OFF and PKCE ON for a confidential client (the plugin sends
  PKCE in both modes; a public client with no secret also works).
- Require PAR OFF.

Then:

```bash
portable/home-stack/scripts/env-set.sh HOME_STACK_HERMES_OIDC_CLIENT_ID
portable/home-stack/scripts/env-set.sh HOME_STACK_HERMES_OIDC_CLIENT_SECRET
launchctl kickstart -k "gui/$(id -u)/<identifier-prefix>.home-stack.hermes"
```

The issuer defaults to this stack's Pocket ID and does not need setting. Verify
with `/api/status`, which should list both `basic` and `self-hosted`: the
password provider is deliberately retained as break-glass, so a broken OIDC
client cannot lock the dashboard out.

Note: while `basic` was the only provider, Hermes' auto-SSO called
`start_login()` on a password-only provider and raised `NotImplementedError` on
every dashboard page load. Configuring a second provider resolves it.

### Rotating the Admin proxy secret

`HOME_STACK_ADMIN_PROXY_SECRET` is what proves to Admin that a request came
through the ingress rather than straight to its loopback port. The generated
Caddyfile references it as `{env.…}`, which Caddy resolves **per request from
its own process environment** — so `hs sync` and `hs reload caddy` cannot pick
up a new or changed value. The daemon has to be restarted:

```bash
sudo launchctl kickstart -k system/<identifier-prefix>.home-stack.caddy
```

Until it is, Caddy forwards the literal placeholder text, Admin's comparison
fails, and it falls back to the Basic Auth prompt. That is the intended failure
mode — a stale secret must never authenticate — but it looks like the feature
silently not working, so check this first.

### Roll back the identity-layer cutover

```bash
portable/home-stack/scripts/cutover-identity.sh --rollback
```

Restores the previous Caddy binary from `.x86_64.bak`, regenerates config from
the registry, and restarts the daemon. Registry entries with `auth:` set are
inert once the plugin is gone only if they are also removed — so the rollback
script reverts `services.yaml` from git as part of the same step.

portable/home-stack/bin/caddy-cloudflare version
portable/home-stack/scripts/status-launchd.sh
```

Caddy rollback:

```bash
mv portable/home-stack/bin/caddy-cloudflare.prev portable/home-stack/bin/caddy-cloudflare
portable/home-stack/scripts/service-launchd.sh restart caddy
```

## Troubleshooting

- **Port conflict:** check `lsof -i :<port>`.
- **Service exits under launchd:** fix the foreground wrapper or service command; do not add shell backgrounding or PID-file supervision.
- **OpenCode auth:** OpenChamber must receive `OPENCODE_SERVER_PASSWORD` when OpenCode runs with `HOME_STACK_OPENCODE_SERVER_PASSWORD`.
- **Proxy identity:** do not override Caddy's default `X-Forwarded-Proto` and `X-Forwarded-Host`; OpenChamber uses them for passkey and WebSocket origin checks.
- **Hermes reports 421/4403 through Caddy:** confirm the generated route has `proxy_identity: upstream` output for both Host and Origin while preserving Caddy's default `X-Forwarded-*` headers.
- **Hermes refuses to start:** verify all three named auth settings exist without printing them, and verify `/api/status` advertises `auth_required: true` plus `basic` before trusting the listener.
- **Caddy reload fails:** regenerate from the reviewed registry with `hs sync`, adapt/validate, check Caddy logs, then retry reload. Restart Caddy only for binary or daemon-level changes.
